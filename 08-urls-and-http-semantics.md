# 08 · URLs and HTTP semantics

A dispatcher shares a link to the shipments dashboard. It opens with the carrier filter **A+B Logistics** selected and scrolls to the results. The dashboard and the API both receive a request for `/shipments`. How does the edge send each request to the right service? And why can neither service find `#results` in its access log?

**The browser sends the path and query, identifies the destination by its HTTP authority, and keeps the fragment for itself.** An HTTP-aware reverse proxy can use the authority and path to choose a service. The service can then use the method and path to choose a handler. Follow the two requests below, then reproduce them on your own machine.

## 1. Take apart a dashboard URL

```text
https://app.example.com/shipments?carrier=A%2BB+Logistics&status=in_transit#results
```

A **URL** (Uniform Resource Locator) identifies a resource and gives a client the information it needs to access it. A **resource** can be a dashboard, a collection of shipments, or a single shipment. The bytes returned for it are a **representation**, such as an HTML document or a JSON array. The same resource can have several representations.

| Part | Value in the link | How it is used |
| --- | --- | --- |
| Scheme | `https` | Selects HTTP over a secured connection. HTTPS defaults to port 443. Plain HTTP defaults to port 80. |
| Authority | `app.example.com` | Identifies the destination host and, when supplied, its port. In `https://app.example.com:8443/` the authority is `app.example.com:8443` and the hostname is `app.example.com`. |
| Path | `/shipments` | Identifies the dashboard route on this host. A path can name a resource generated by code without corresponding to a file on disk. |
| Query | `carrier=A%2BB+Logistics&status=in_transit` | Part of the request target. This application reads two filter values. The endpoint defines which names, repetitions, and values have meaning. |
| Fragment | `results` | Interpreted by the client after selecting the resource. In this HTML page, `#results` points to an element with `id="results"`. A frontend router can also read a fragment. |

The `?` and `#` introduce their respective components. For an ordinary HTTP(S) URL the **origin** is the scheme, hostname, and effective port together. `https://app.example.com` and `https://app.example.com:443/shipments` have the same origin. Changing the hostname to `api.example.com`, the port to `8443`, or the scheme to `http` gives a different origin. Changing the path, query, or fragment keeps the origin.

Two other authority forms are worth recognizing. Brackets enclose an IPv6 literal, as in `https://[2001:db8::12]:8443/shipments`. Generic URL syntax also allows *userinfo* before an `@`. Its use in HTTP(S) URLs is deprecated. Supply credentials using the application's authentication mechanism. [URI components](https://www.rfc-editor.org/rfc/rfc3986.html#section-3) · [HTTP(S) schemes and userinfo](https://www.rfc-editor.org/rfc/rfc9110.html#section-4.2) · [Browser URL origins](https://url.spec.whatwg.org/#origin)

### Resolve a link against its base

Suppose the base URL is `https://app.example.com/dispatch/today?sort=eta`. The browser resolves a relative reference before it can make a request.

| Reference | Resolved URL |
| --- | --- |
| `shipments/S42` | `https://app.example.com/dispatch/shipments/S42` |
| `/shipments/S42` | `https://app.example.com/shipments/S42` |
| `?page=2` | `https://app.example.com/dispatch/today?page=2` |
| `#results` | `https://app.example.com/dispatch/today?sort=eta#results` |

A final slash matters. With `/dispatch/today/` as the base path, `shipments/S42` resolves under `/dispatch/today/`. Without the final slash, the last base segment is replaced. The same rule helps explain why a relative `Location` header can land a client on an unexpected route. Try any row with `new URL(reference, base).href` in a browser console. [Relative URL resolution](https://developer.mozilla.org/en-US/docs/Web/API/URL_API/Resolving_relative_references)

## 2. Follow the document and API requests

**Request 1 loads the page.** The browser navigates to the shared link. Here are the relevant fields as an HTTP/1.1 request to the dashboard's public edge.

```http
GET /shipments?carrier=A%2BB+Logistics&status=in_transit HTTP/1.1
Host: app.example.com
Accept: text/html
```

For this ordinary *origin-form* request, the target on the first line contains the path and query. `Host` carries the authority, including a nondefault port if present. The scheme is implicit in the receiving connection and its configuration. An HTTP/1.1 client requesting a URL with an empty path sends `/`. Other forms serve special purposes, including an absolute URL at a forward proxy and a host and port for the classic `CONNECT` tunnel request. [HTTP/1.1 request targets](https://www.rfc-editor.org/rfc/rfc9112.html#section-3.2)

**Request 2 loads the rows.** The page's JavaScript builds a URL under `https://api.example.com`, copies the two filters, and asks for JSON. The address bar still shows the dashboard. An API call to `/shipments` would have no query if the code built it without the filters.

```http
GET /shipments?carrier=A%2BB+Logistics&status=in_transit HTTP/1.1
Host: api.example.com
Accept: application/json
```

Either request can also use HTTP/2 or HTTP/3. Here is the second one's decoded field view. On the wire these versions use frames. The response status is carried in `:status`.

```text
:method     = GET
:scheme     = https
:authority  = api.example.com
:path       = /shipments?carrier=A%2BB+Logistics&status=in_transit
accept      = application/json
```

| Decision | Component and evidence in this deployment |
| --- | --- |
| Which network endpoint can I contact? | DNS resolves each hostname. Both can point to the same public edge at `203.0.113.80`. The hostname is sufficient for the address lookup. An IP router uses the destination IP to forward packets. |
| Which TLS service am I connecting to? | On a fresh HTTPS connection, SNI can help the edge select its TLS configuration. The client verifies the expected hostname against the certificate. The path and query travel inside the protected HTTP exchange. |
| Which service receives this HTTP request? | After TLS termination, the edge uses its routing configuration. Here `app.example.com` + `/shipments` goes to the dashboard, `api.example.com` + `/shipments` goes to the shipment service, and `api.example.com` + `/labels` goes to the label service. A TCP pass-through load balancer needs a downstream HTTP component for path routing. |
| Which code runs, and which data may it return? | The shipment service matches a handler such as `GET /shipments` or `GET /shipments/{id}`, parses its parameters, and authorizes the user for the requested data. A path match establishes which code handles a request. The authorization check establishes whose records it may return. |
| Who uses `#results`? | The browser. It can scroll or change local UI state without another fetch. JavaScript can explicitly send a value it reads from `location.hash` in a **new** request. That creates a separate disclosure. |

The edge makes a separate upstream request. It might preserve the public host and path, or rewrite them according to its configuration. In the previous lesson the API listener was `10.20.0.12:8443`. That private socket address alone tells you neither the forwarded HTTP authority nor the selected handler. To establish those, compare the edge route with what the application received. [HTTP/2 request fields](https://www.rfc-editor.org/rfc/rfc9113.html#section-8.3.1) · [HTTP/3 fields](https://www.rfc-editor.org/rfc/rfc9114.html#section-4.3) · [NGINX virtual servers and path matching](https://nginx.org/en/docs/http/request_processing.html) · [URI fragments](https://developer.mozilla.org/en-US/docs/Web/URI/Reference/Fragment)

## 3. Encode data and normalize URLs

**Percent encoding** writes one byte as `%` followed by two hexadecimal digits. A delimiter such as `&` can structure a query or be part of a carrier's name. Encoding the *value* preserves that distinction. For non-ASCII text, a browser using UTF-8 first converts the character to bytes. The `é` in `café` takes the two bytes `C3 A9`, so the encoded value is `caf%C3%A9`.

| Intended data | Example spelling | What the reader gets |
| --- | --- | --- |
| A literal plus | `carrier=A%2BB` | The value `A+B`. |
| A space in a form-style query | `city=New+York` or `city=New%20York` | `URLSearchParams` reads both as `New York`. In a path segment, a literal `+` stays a plus. |
| An ampersand or hash inside a value | `label=R%26D%231` | One value, `R&D#1`. A raw `&` would separate form fields and a raw `#` would start the URL fragment. |
| Two values with the same name | `tag=air&tag=cold` | `getAll("tag")` returns both in order. `get("tag")` returns the first. The API contract decides whether repeats are a list or an error. |

The query component is a string. The familiar `name=value&name=value` syntax and the space meaning of `+` belong to the form encoding used by `URLSearchParams`. Build a URL from unencoded values so the serializer can encode each component exactly once.

```js
const link = new URL("/shipments", "https://app.example.com");
link.searchParams.set("carrier", "A+B Logistics");
link.searchParams.set("status", "in_transit");
link.hash = "results";

console.log(link.href);
// https://app.example.com/shipments?carrier=A%2BB+Logistics&status=in_transit#results
console.log(link.searchParams.get("carrier")); // A+B Logistics
```

Passing the already encoded string `A%2BB` to `set` makes the percent sign data, so the serializer produces `A%252BB`. Applying a decoder to the *whole* URL before identifying its components also changes the meaning of delimiters. Parse the URL first, then consume the values exposed by the parser. [Browser URL and form encoding](https://url.spec.whatwg.org/#application/x-www-form-urlencoded) · [URLSearchParams examples](https://developer.mozilla.org/en-US/docs/Web/API/URLSearchParams)

**Normalization** is choosing a standard spelling where equivalence is defined. For example, `new URL("HTTPS://API.Example.COM:443/dispatch/../shipments").href` produces `https://api.example.com/shipments`. The browser normalizes scheme and hostname case, omits the default port, and resolves dot segments. A routing decision about a path needs more care.

| Comparison | What you may conclude |
| --- | --- |
| `/shipments/S42` and `/shipments/s42` | Paths can be case-sensitive. The service defines the meaning of these IDs. |
| `/shipments` and `/shipments/` | The two paths may have different handlers. Some services redirect one to their preferred spelling. |
| `/labels/A%2FB` and `/labels/A/B` | `/` separates path segments. Decoding an encoded slash before splitting the path can change the segment count. Check which forms the service accepts and how its proxy forwards them. |
| `?sort=eta&sort=id` and `?sort=id&sort=eta` | Order can express sort priority. Reordering or discarding duplicates can change the requested result. |

For an AppSec review, compare the proxy's route, the framework's parsed parameters, and the resource used by the permission check. Agree on how to handle ambiguous inputs and authorize the resource the handler actually selected. For sensitive URLs, record a route template and request ID so an investigation can correlate decisions without copying customer data into logs. [URI equivalence and normalization](https://www.rfc-editor.org/rfc/rfc3986.html#section-6) · [OWASP REST input validation and access control](https://cheatsheetseries.owasp.org/cheatsheets/REST_Security_Cheat_Sheet.html)

## 4. Read a request and response as a pair

The dispatcher creates a shipment. The operation applies to the collection `/shipments`. The JSON in the request describes the proposed shipment. The JSON in the response describes the result. These HTTP/1.1 excerpts omit unrelated headers. The one-line bodies have no trailing newline.

```http
POST /shipments HTTP/1.1
Host: api.example.com
Content-Type: application/json
Accept: application/json
Content-Length: 42

{"origin":"Tabriz","destination":"Tehran"}
```

```http
HTTP/1.1 201 Created
Location: /shipments/S42
Content-Type: application/json
Content-Length: 30

{"id":"S42","status":"queued"}
```

Read the first line, then the headers, then the body. A request line names the **method**, **target**, and **HTTP version**. A response status line supplies a numeric **status code** and may include a human-readable reason phrase. Software acts on the number. In HTTP/1.1 an empty line ends the header section. `Content-Length` here counts the body bytes, excluding that empty line. HTTP/1.1 can also delimit a body with chunked transfer coding. HTTP/2 and HTTP/3 carry the same semantics using frames on streams. [HTTP messages](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Messages) · [HTTP/1.1 body length](https://www.rfc-editor.org/rfc/rfc9112.html#section-6.3)

### What the headers tell you

| Field | Question it answers |
| --- | --- |
| `Host` or `:authority` | Which host and optional port is the request targeting? A browser request **from** the dashboard **to** the API targets `api.example.com`. If it contains `Origin: https://app.example.com`, that field describes the initiating origin. |
| `Content-Type` | How should the recipient interpret this message's content? In the example both sender and responder chose JSON. |
| `Accept` | Which response media types does the client prefer? A client can send JSON and request a different response format. |
| `Accept-Encoding` and `Content-Encoding` | Which content codings can the client receive, and which did the sender apply? A gzip-compressed JSON response can have `Content-Type: application/json` and `Content-Encoding: gzip`. Its `Content-Length`, if present, counts the coded bytes. |
| `Authorization`, `Cookie`, `Set-Cookie` | The first two can carry request credentials. A server can use `Set-Cookie` in a response to establish or update a cookie. Each request needs enough context for the application to associate it with a user and check permission. |
| `Location` | Which URL identifies the primary resource created by this `201`, or the destination of a redirect? The status determines how to interpret the field. |

Header **names** are case-insensitive. Rules for **values** depend on the field. Preserve case in values such as credentials and entity tags. HTTP is **stateless** in the sense that a server interprets each request using that request's context. A session store can still hold application state, and the same transport connection can carry many requests.

### Choose the body format and its parser

| Media type | Example and interpretation |
| --- | --- |
| `application/json` | A shipment object has named fields and typed values. Valid JSON can still fail business validation, such as an unknown city ID. |
| `application/x-www-form-urlencoded` | `origin=New+York&destination=Tehran` encodes form fields in the body. The same convention can appear in a URL query. Inspect the target and the body separately. |
| `multipart/form-data` | A form with a label file and text fields has multiple parts. The `boundary` parameter tells the parser where they start and end. When sending browser `FormData` with `fetch`, let the browser generate the content type and matching boundary. |
| `text/html; charset=utf-8` or `application/pdf` | The dashboard can return an HTML document, while a label endpoint returns PDF bytes. A `200` response alone says nothing about which parser to use. |

**Content negotiation** lets the client express preferences and the server select a representation. For example, a shipment endpoint might serve JSON to `Accept: application/json` and HTML to `Accept: text/html`. If a cache can reuse the responses and the choice depends on `Accept`, `Vary: Accept` tells it to account for that request header. An API that enforces its supported formats can return `415` for an unsupported request media type or `406` when it cannot supply an acceptable response. [Content negotiation](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Content_negotiation) · [Cache variants](https://www.rfc-editor.org/rfc/rfc9111.html#section-4.1) · [FormData and boundaries](https://developer.mozilla.org/en-US/docs/Web/API/XMLHttpRequest_API/Using_FormData_Objects)

URLs often end up in browser history, copied links, and edge access logs. A page URL may also contribute path or query information to a `Referer` header depending on referrer policy. Browsers exclude the fragment from that header, although page scripts can read it. Keep passwords, session IDs, and bearer credentials out of URLs. HTTPS protects the request on its way to the TLS endpoint. Headers and bodies are readable at that endpoint too, so redact credentials there when logging. [Referer and referrer policy](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Referer) · [OWASP guidance on sensitive request data](https://cheatsheetseries.owasp.org/cheatsheets/REST_Security_Cheat_Sheet.html#sensitive-information-in-http-requests)

## 5. Choose a method and decide whether to retry

**Safe** asks what the client requested. A safe method asks for a read-only operation. A server can still write an access log or update metrics. A link that cancels a shipment on `GET` breaks this promise. A browser prefetch or link preview could cancel the shipment simply by opening the link.

**Idempotent** asks what happens if the same request reaches the server twice. The intended effect of repeating an idempotent request is the same as applying it once. The response status, timestamp, or log entries can differ. **Cacheable** asks a third question about storing and reusing a response under HTTP cache rules. For example, `PUT` is idempotent and its response is not cacheable.

| Method | What the client asks for | Safe? | Idempotent by definition? |
| --- | --- | --- | --- |
| `GET` | Retrieve a representation, such as the filtered shipment list. | Yes | Yes |
| `HEAD` | Get the response headers for a corresponding `GET`, with no response body. Some fields that require generating the content may be omitted. | Yes | Yes |
| `POST` | Ask the target to process submitted data. Creating a shipment in a collection is one use. | No | No |
| `PUT` | Create or replace the state of a resource at the given target, such as `/shipments/S42`, with the supplied representation. | No | Yes |
| `PATCH` | Apply changes described by a patch document. Setting a field to a value and incrementing a counter behave differently on repetition. | No | No |
| `DELETE` | Remove the target resource's association with its URI. The application may retain an audit record. | No | Yes |
| `OPTIONS` | Ask about communication options for a target. One use is a browser's cross-origin preflight. | Yes | Yes |

Method names are case-sensitive. Browser `fetch` accepts no request body for `GET` or `HEAD`, and HTTP gives content in those requests no generally defined meaning. For a complex read, an API may explicitly support `QUERY`, a safe, idempotent method that carries query content. Other specialized methods include `CONNECT` for a tunnel and `TRACE` for a diagnostic loopback. Supported methods depend on the endpoint. [Method registry](https://www.iana.org/assignments/http-methods/http-methods.xhtml) · [HTTP methods](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Methods) · [PATCH](https://www.rfc-editor.org/rfc/rfc5789.html#section-2) · [QUERY](https://www.rfc-editor.org/rfc/rfc10008.html#section-2)

### A timeout after the database commit

The API creates shipment `S42`, but the network drops the `201` before the dashboard receives it. From the dashboard's point of view, the outcome is **unknown**.

- **Repeating a create.** A second ordinary `POST /shipments` could create `S43`. For APIs that support an idempotency key, send one key for the logical create and reuse it on retries with the same payload. The server must associate the key with the caller, operation, and result and coordinate that record with creation so concurrent attempts cannot create two rows. Follow the API's key lifetime and payload-mismatch rules.
- **Repeating a delete.** A first `DELETE /shipments/S42` might return `204` and a second `404`. If nothing recreates the resource between calls, the final intended state is the same.
- **Protecting someone else's edit.** Two dispatchers read a shipment with the strong entity tag `ETag: "s42-v3"`. One saves a change, producing a new tag. The other's `PUT` with `If-Match: "s42-v3"` can receive `412 Precondition Failed`. The second dispatcher can now reload and reconcile the edits. This solves a different problem from duplicate creation. [Idempotency and retries](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.2.2) · [Conditional requests](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Conditional_requests)

## 6. Interpret a status code in context

Read the method, status, relevant headers, and response content together. **1xx** supplies interim information, **2xx** indicates success, **3xx** calls for further action such as following a location or reusing a stored representation, **4xx** reports a problem fulfilling this request, and **5xx** reports a server-side failure. A proxy can generate a response itself, so the status alone does not identify the component that made the decision.

| Status | How to read it in a shipment workflow |
| --- | --- |
| `200 OK`, `201 Created` | A list read succeeded, or a create succeeded. A `201` with `Location: /shipments/S42` identifies the created resource. |
| `202 Accepted`, `204 No Content` | A label job was accepted for processing and may still fail later. A `204` means the operation succeeded and the response has no content to parse. |
| `304 Not Modified` | For a conditional `GET` or `HEAD`, the client can reuse its stored representation. For example, it sent `If-None-Match` with a matching `ETag`. The `304` has no body. |
| `400 Bad Request`, `422 Unprocessable Content` | With a JSON-only create endpoint, malformed JSON can yield `400`. A well-formed object with an unknown destination city can yield `422`. Check the API's error contract for field names and messages. |
| `401 Unauthorized`, `403 Forbidden` | A `401` means the request lacks valid authentication credentials and includes a `WWW-Authenticate` challenge. A `403` means the server understood the request and refuses it, for example because the dispatcher lacks access to that shipment. |
| `404 Not Found`, `405 Method Not Allowed` | A `404` can mean an unmatched route, a missing record, or a server choosing to conceal its existence. A `405` means the method is unsupported for this target. The response must include `Allow` with the currently supported methods. |
| `406 Not Acceptable`, `415 Unsupported Media Type` | For `406`, inspect preferences such as `Accept` and the available response formats. For `415`, inspect the submitted `Content-Type`, content coding, and actual bytes. |
| `409 Conflict`, `412 Precondition Failed` | A transition can conflict with current business state, such as canceling an already delivered shipment. A `412` identifies a failed request condition such as `If-Match`. |
| `413 Content Too Large`, `429 Too Many Requests` | Check the upload-size limit or rate limit at the component that responded. A `429` may include `Retry-After` as a delay in seconds or an HTTP date. Retry only when the operation permits it. |
| `500 Internal Server Error`, `503 Service Unavailable` | A server encountered an unexpected failure, or is temporarily unable to serve the request. A `503` can also carry `Retry-After`. |
| `502 Bad Gateway`, `504 Gateway Timeout` | A gateway reports a failure obtaining a valid upstream response, or a timeout waiting for the upstream. Inspect that gateway's upstream timing and error logs. |

A browser's `fetch` normally fulfills its promise when it receives a readable `404` or `422` response. The frontend can inspect `response.status`, `response.ok` (true for 200–299), and the declared response format. Skip body parsing for a `204` or a response to `HEAD`. A network error or a browser policy failure can instead reject the promise without exposing an HTTP response to JavaScript. [HTTP status codes](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Status) · [IANA status registry](https://www.iana.org/assignments/http-status-codes/http-status-codes.xhtml) · [Using Fetch](https://developer.mozilla.org/en-US/docs/Web/API/Fetch_API/Using_Fetch)

## 7. Follow a redirect one request at a time

A redirect response can give the client a new target in `Location`. If the client follows it, it makes **another HTTP request**. Resolve a relative `Location` against the URL that produced the response. Then check which method, content, and destination the follow-up uses.

| Code | Meaning | What happens to a submitted `POST` if followed? |
| --- | --- | --- |
| `301 Moved Permanently` | A permanent move | A user agent may change the `POST` to `GET` and drop the body. |
| `302 Found` | A temporary move | The same historical `POST`-to-`GET` behavior is allowed. |
| `303 See Other` | Retrieve a representation at the new location | A browser normally follows with `GET` and no submitted body. HTTP also permits a `HEAD` retrieval. |
| `307 Temporary Redirect` | A temporary move preserving the method | The client reissues `POST` with the original content. |
| `308 Permanent Redirect` | A permanent move preserving the method | The client reissues `POST` with the original content. |

Consider an HTML form that has just created shipment `S42`. The server selects the following exchange so the results page can be refreshed independently of the submission.

```text
1. Browser sends     POST /shipments              with the form body
2. Server responds   303 See Other                Location: /shipments/S42
3. Browser sends     GET /shipments/S42           with no form body
4. Server responds   200 OK                       with the detail page
```

Refreshing the final page repeats the `GET`. An API can instead finish the original create with `201` and a `Location` that identifies the new shipment. A `304` belongs to cache revalidation and sends the client back to its stored content.

If a redirect points to another origin, the next request has a different destination. Especially for `307` and `308`, consider who will receive the body. For an application-controlled “return to” link, resolve the destination with a URL parser and check its origin against allowed destinations. A fragment can survive a redirect in the address bar when `Location` supplies no fragment of its own. The browser carries that fragment locally across the navigation. [Redirect semantics](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.4) · [Location and fragment inheritance](https://www.rfc-editor.org/rfc/rfc9110.html#section-10.2.2) · [MDN redirection guide](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Redirections)

## 8. Find the component that made the decision

The dashboard shows “Could not load shipment.” Open the browser's **Network** panel, preserve the log, and reproduce the action. Select the request that loads the data. Compare its URL, method, initiator, status, redirect history, content type, and response with what the frontend expected. Then correlate it with the edge and application logs.

| Observation | Next evidence to collect |
| --- | --- |
| Only the dashboard document appears. | Check whether the frontend issued the fetch, whether its URL was constructed successfully, and whether the console reports a browser policy failure. |
| The API request exists but omits `carrier`. | Compare the document URL with the API request target. The frontend builds the second URL and decides which fields to copy. |
| The API call ends in `200 text/html` and JSON parsing fails. | Inspect the authority, redirect chain, and response preview. A login redirect or a dashboard fallback can return a perfectly valid HTML document. |
| A `404` appears at the public edge. | Check the matched virtual host and route, any rewrite, and whether the edge recorded an upstream response. Compare the upstream method and path with the application's route and record lookup. |
| The browser reports a DNS or TLS error with no HTTP status. | Investigate name resolution or peer verification at the failing connection. If the browser received an HTTP `502`, it did reach an HTTP responder. Inspect that responder's next hop. |

For example, these **illustrative** log entries explain one particular `404`. The ID is assigned at the edge and carried to the service. Field names vary by deployment.

```text
edge  id=r17 host=api.example.com method=GET path=/shipments/S42 route=shipments upstream_status=404
api   id=r17 method=GET path=/shipments/S42 handler=readShipment lookup=missing status=404
```

The gateway selected the shipment service. The matching application event shows that the handler ran and the lookup missed. A different `404` produced by the edge before forwarding would need different evidence, such as a route-miss entry there. An absent application log by itself is inconclusive when sampling or retention can drop events. [Chrome DevTools Network reference](https://developer.chrome.com/docs/devtools/network/reference)

## 9. Observe two hosts on one local listener

This lab uses Node.js, curl, and a browser. It runs entirely on IPv4 loopback without packages, certificates, or a hosts-file change. One HTTP listener serves two authorities. `localhost:8765` serves the HTML dashboard. `127.0.0.1:8765` serves the JSON API. Both use the path `/shipments`. The API permits this dashboard origin to read the demo response.

### Start the example

Paste the block into terminal A in a shell such as Bash or Zsh. Leave it running. The server prints the method, authority, and raw request target it receives.

```sh
node --input-type=module <<'JS'
import { createServer } from "node:http";

const dashboard = new URL("http://localhost:8765");
const api = new URL("http://127.0.0.1:8765");
const shipments = [
  { id: "S42", carrier: "A+B Logistics", status: "in_transit" },
  { id: "S43", carrier: "Northline", status: "queued" },
];

const page = `<!doctype html><meta charset="utf-8"><title>Shipments</title>
<h1 id="top">Shipments</h1><p id="results">Loading…</p><a href="#top">Top</a>
<script type="module">
  const endpoint = new URL("/shipments", "http://127.0.0.1:8765");
  endpoint.search = location.search;
  const output = document.querySelector("#results");
  try {
    const response = await fetch(endpoint, { headers: { Accept: "application/json" } });
    if (!response.ok) throw new Error("HTTP " + response.status);
    const rows = await response.json();
    output.textContent = rows.map(row => row.id).join(", ") || "No matches";
  } catch (error) {
    output.textContent = error.message;
  }
</script>`;

createServer((req, res) => {
  const host = req.headers.host;
  console.log(req.method, host, req.url);

  function send(status, body = "", headers = {}) {
    res.writeHead(status, {
      "Content-Length": Buffer.byteLength(body),
      "Cache-Control": "no-store",
      ...headers,
    });
    res.end(req.method === "HEAD" ? undefined : body);
  }

  if (host !== dashboard.host && host !== api.host) return send(404);
  let target;
  try {
    target = new URL(req.url, api);
  } catch {
    return send(400);
  }

  if (host === api.host && target.pathname === "/views/in-transit") {
    if (req.method !== "POST") return send(405, "", { Allow: "POST" });
    return send(303, "", { Location: "/shipments?status=in_transit" });
  }
  if (target.pathname !== "/shipments") return send(404);
  if (!["GET", "HEAD"].includes(req.method)) return send(405, "", { Allow: "GET, HEAD" });
  if (host === dashboard.host) {
    return send(200, page, { "Content-Type": "text/html; charset=utf-8" });
  }

  const carrier = target.searchParams.get("carrier");
  const status = target.searchParams.get("status");
  const rows = shipments.filter(row =>
    (carrier === null || row.carrier === carrier) && (status === null || row.status === status)
  );
  send(200, JSON.stringify(rows), {
    "Content-Type": "application/json",
    "Access-Control-Allow-Origin": dashboard.origin,
  });
}).listen(8765, "127.0.0.1", () => console.log("Listening on 127.0.0.1:8765"));
JS
```

### Compare the address bar with the two requests

1. Open DevTools **Network** in a fresh browser tab, then navigate to `http://localhost:8765/shipments?carrier=A%2BB+Logistics&status=in_transit#results`. The page should display shipment **S42**.
2. Select the **document** request and the **fetch** request. Compare the authority, content type, and response. Both request targets carry exactly the filters in the address bar. The API parsed `A%2BB+Logistics` as `A+B Logistics` and matched the first shipment.
3. Click **Top**. The address bar now ends in `#top`. Check terminal A for another shipment request. A same-document fragment change on this page requires none.
4. Change the query in the address bar to `?carrier=Northline&status=queued#results` and press Enter. Predict the matching ID before checking the page and the two new log entries.

For the first navigation, the two relevant server lines should read as follows. The browser may also request a favicon.

```text
GET localhost:8765 /shipments?carrier=A%2BB+Logistics&status=in_transit
GET 127.0.0.1:8765 /shipments?carrier=A%2BB+Logistics&status=in_transit
```

### Inspect the exchange with curl

Run these commands in terminal B. Keep the URLs quoted so the shell passes `&` and `#` through as part of the argument.

```sh
curl --noproxy '*' -sS -i 'http://localhost:8765/shipments?carrier=A%2BB+Logistics#results'
curl --noproxy '*' -sS -i 'http://127.0.0.1:8765/shipments?carrier=A%2BB+Logistics#results'
curl --noproxy '*' -sS -I 'http://127.0.0.1:8765/shipments?status=queued'
curl --noproxy '*' -sS -v -L --data '' -o /dev/null 'http://127.0.0.1:8765/views/in-transit'
```

| Command | Evidence to look for |
| --- | --- |
| First and second | `-i` prints response headers and body. The first is HTML, the second JSON containing `S42`. Both went to the same listener and path. `Host` selected the dashboard or API handler. curl prints the HTML source without executing its JavaScript. |
| Third | `-I` sends `HEAD`. The JSON endpoint returns metadata including the length its `GET` body would have. There is no response body. Use a real `GET` when investigating a `GET` handler. |
| Fourth | `--data ''` starts an empty `POST` and `-L` follows redirects. In verbose output, `>` shows outgoing request lines and `<` incoming response lines. Observe `POST /views/in-transit`, then `303` with `Location`, then `GET /shipments?status=in_transit` and `200`. |

The second browser query displays **S43**. To relate a visible result to the protocol, identify the API request in the browser, the raw target in terminal A, and the row returned in the JSON response. Stop the listener with **Ctrl-C** in terminal A. ## 10. Check your understanding

1. A browser opens `https://api.example.com:8443/shipments/S42?units=kg#events` over HTTP/1.1. What does the first request line contain? What is the `Host` value? Where does `events` go?
2. Two websites share an IP, port, and public edge. Both have a `/shipments` route. What distinguishes the services after TLS termination? What evidence identifies the selected upstream?
3. A carrier is literally named `A+B Logistics`. Why does `carrier=A+B+Logistics` match a different value in a form-style query? How would you construct it correctly?
4. The base URL is `https://api.example.com/v1`. A developer passes `"shipments"` to `new URL` with that base and expects `/v1/shipments`. Which path will the browser request?
5. After a `POST` times out, a dispatcher clicks “Create” again. What would allow the API to return the result of the first create? Would an `If-Match` header on an unrelated `PUT` solve this problem?
6. A form response should lead to a read-only confirmation page. Which redirect communicates this? Which temporary redirect would preserve the submitted method and body?
7. A client sends syntactically valid JSON naming an unknown city. How does that differ from sending XML to a JSON-only endpoint, or asking for a response in a format the API cannot serve?
8. A fetch for shipment details finishes with `200` but the frontend reports an error parsing JSON. What would you inspect before changing the parser?

### Answer key

1. `GET /shipments/S42?units=kg HTTP/1.1` and `Host: api.example.com:8443`. The browser retains `events` as the fragment and can use it after retrieval.
2. The HTTP authority distinguishes the virtual hosts. Check the edge's matched host and route, any rewrite, and an upstream entry correlated to the service's request log.
3. A form parser reads each raw `+` as a space, giving `A B Logistics`. Pass `"A+B Logistics"` to `searchParams.set("carrier", value)`. The query then contains `carrier=A%2BB+Logistics`.
4. `/shipments`. The base's last segment is replaced. Use the base `https://api.example.com/v1/` or give the root-relative path `/v1/shipments` to select the intended resource.
5. A create endpoint with durable deduplication can recognize a repeated key for the same caller, operation, and payload and return the recorded result. `If-Match` on an update protects against editing a stale representation.
6. `303 See Other` directs the client to retrieve the confirmation resource. `307 Temporary Redirect` preserves the method and content when followed.
7. Under the example API's contract these yield `422` for a semantic validation error, `415` for the unsupported request format, and `406` for the unsatisfied response preference when enforced.
8. Check the fetch URL and authority, intermediate redirects, final `Content-Type`, and the response preview. An HTML login or dashboard page points to routing or session handling. A JSON response with malformed content points to the producer.
